# Acceptance criteria

Status is `PASS`, `FAIL` or `NOT VERIFIED`, with evidence. Nothing is marked PASS until it has been run.

| Criterion | Status | Evidence |
|---|---|---|
| Healthy reference and current windows produce a documented baseline | PASS (synthetic data) | `test_healthy_baseline_false_alarm_rate`: 100 seeded windows, 0 window drift, 3 with a single input flagged, 1 score flag; recorded in `docs/ARCHITECTURE.md` 3.5. Not tested on real traffic. |
| Invalid schema or data quality issue is detected | PASS (window level) | `tests/unit/test_data_quality.py` (missing column, unparseable and non-integer values, unseen category, out of range, missing values, duplicate IDs, undersized window) and `test_hard_quality_failure_blocks_drift_evaluation`. The seeded `schema_break` scenario (a `contract` field missing from every observation) yields `invalid_input` for both drift and performance, tested end to end from files (`test_scenario_produces_the_documented_signals`). A live service rejects such requests with a 422, so a real schema break would reach the observation files only from a different producer; that path was simulated, not observed. |
| Synthetic shifted data produces a report/signal under configured assumptions | PASS | `test_shifted_window_is_drift_and_names_the_shifted_inputs`; `test_cli_writes_json_and_html_for_a_shifted_window` writes the JSON result and Evidently HTML from observation files. |
| Prometheus collects service request, error and latency metrics | PASS (local, limited) | `tests/integration/test_stack.py` against the real stack (9 passed, 169 s, 2026-10-27): both targets up, 3 successful and 3 rejected (4xx) `/predict` requests counted, latency histogram queryable, labels limited to method/route/status_class. A live error burst was also run: with the service started without a model (`compose.incident.yaml`), 45 requests all returned 5xx, `model_loaded` fell to 0 and the 5xx ratio exceeded 50% in Prometheus. The alerts that watch these signals need 2 to 5 minutes of sustained failure; the test did not wait for them to fire, and their timing is covered by promtool with synthetic series. |
| Grafana dashboards show service and ML-related signals | PASS (API level); look approved by the owner | The same test provisions the dashboard, runs all 21 panel queries through Grafana (none errors) and confirms 12 key service, model, drift and performance panels return data. On 2026-10-27 the owner viewed the running dashboard (the `input_shift` incident loaded, live traffic) and approved how it looks: "simple yet functional". That was a look at one state, not the step-by-step `docs/MANUAL_CHECKLIST.md`: the healthy and failure states and the alert text on the page were not walked through, and no screenshots exist. The font, corner radius and panel background from the design system could not be applied in Grafana. |
| Alerts contain an actionable description and runbook reference | PASS | `test_every_alert_has_severity_description_and_a_runbook_section` (9 rules, each runbook anchor exists); promtool rule tests including silent cases; the live `DataDriftDetected` and `ModelPerformanceDegraded` alerts were observed firing with their `runbook_url`. Runbook commands checked against the running stack: health, `df` on the observation volume, uid 10001, and the error-burst recovery (`docker compose up -d service`, readiness, `model_loaded` back to 1). Not exercised: reading `model load failed` reasons from the log with `findstr`, and the individual non-recovery causes (checksum mismatch and the like). |
| Delayed labels can be joined to prior predictions and evaluated | PASS (synthetic data) | `tests/unit/test_delayed_evaluation.py` (16 tests): join on `event_id`, metrics from labelled rows only (unlabelled rows cannot change them), late labels pending until the cut-off, labels dated before their prediction excluded, labels for other windows counted, conflicting or unparseable labels rejected, undefined metrics `None` not 0, too few labels or one class gives no verdict. The live stack evaluated a seeded window and pushed it, and the dashboard showed it. Labels here are generated, not from a real labelling process. |
| Drift is not automatically treated as proof of performance loss | PASS | Every drift and performance result carries a note saying so, and `test_drift_and_accuracy_loss_are_independent` shows all three combinations on seeded data: drift with a fall in AUC (`input_shift`, 0.689), drift without one (`benign_shift`, 0.784), and a fall with no drift (`concept_shift`, 0.196). The drift alert's text states it does not show lower accuracy (`test_drift_alert_never_claims_accuracy_loss`). |
| Logs and metrics follow data-minimization and cardinality rules | PASS (service only, limited scope) | `tests/contract/test_observability.py`: 30 distinct requests collapse to one `http_requests_total` series, label names limited to method/route/status_class, and event IDs, request IDs and feature values are absent from `/metrics` and from formatted log output. The pushed drift metrics use only status, manifest feature and issue-code labels (`test_labels_are_bounded_and_carry_no_data_values`), and the live Prometheus label set was checked. The observation files were confirmed to omit `customer_id`. The pushed performance metrics use a `status` label only (`test_performance_labels_are_bounded`), and simulated observations contain only the documented fields. Not a full audit. |
| README explains thresholds, limitations, local setup and incident simulation | PASS (one reader, one machine) | `README.md` has a thresholds table with how it was calibrated, a limitations list, a quick start, the incident table and the design choices with the alternatives rejected. I ran its quick start literally in a fresh clone of the branch on Windows: `uv sync`, lint, mypy and 150 tests; `docker compose up --build`; one prediction with an `X-Event-ID`; the `input_shift` simulation and both jobs pushed; Prometheus then showed drift on 4 of 10 inputs, AUC 0.689 and both alerts firing, and the dashboard was provisioned; the live-observation snippet; `down -v`. It worked as written after one fix (the `&&` chains did not run in Windows PowerShell 5.1). The same clone then passed all 9 stack tests (154 s). The person who ran it is also its author; no independent contributor has tried it, and macOS and Linux were not tried locally. |

## Definition of done

| Item | Status | Evidence |
|---|---|---|
| A new contributor can follow the README from a clean environment | PASS (see the README row for the limits) | Fresh-clone run described above. |
| The documented happy path works end to end | PASS | Same run: service, scrape, simulation, both jobs, push, alerts, dashboard provisioning. |
| Automated tests and quality checks pass in the available environment | PASS (locally) | Fresh clone: ruff, format check, mypy strict and 150 tests; 9 stack tests with `RUN_STACK_TESTS=1`. Also passes in CI on a Linux runner (next row). |
| At least one meaningful failure scenario is demonstrated | PASS | Live error burst and recovery in the stack tests, plus five seeded simulations (`docs/RUNBOOK.md`). |
| Architecture, configuration, security assumptions, limitations and operational recovery are documented | PASS (unreviewed by anyone else) | `docs/ARCHITECTURE.md`, `README.md`, `docs/RUNBOOK.md`; the local-only Grafana credentials and loopback-only ports are called out. |
| CI runs the agreed checks on pull requests | PASS (one pull request, one repository) | `.github/workflows/ci.yml` passes `actionlint` and ran on pull request #1 on a GitHub Linux runner. The first run failed one test: the reference check compares freshly built files with committed ones byte for byte, and the committed JSON had Windows line endings. The fix makes every generated text file write `\n` on any platform. The next run passed both jobs: `checks` (ruff, format check, mypy strict, 150 tests) and `stack` (9 Docker tests in 213 s, confirmed as run and not skipped). It has not yet run on a push to the default branch, and the repository is private, so the run is not publicly visible. |
| No secrets or private data are committed | PASS (scan, not an audit) | Searched tracked files for key, token, password and private-key patterns and for personal paths: the only hit is the documented fixed Grafana password for the loopback-only demo, plus deliberate fake values in tests. All data is synthetic. |
| All acceptance criteria have evidence-backed statuses | Done | All ten criteria above are marked PASS with their limits stated. For the Grafana criterion the queries and data are verified by test and the look was approved by the owner; the full manual checklist and screenshots are not done. |
